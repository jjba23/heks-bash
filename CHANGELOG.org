#+title: heks-bash release notes
#+author: Josep Bigorra
#+email: jjbigorra@gmail.com

This file records what each release changed and what it breaks, newest first.
It is history, not a plan: the guide says what the configuration does, this says
when it started doing it.  The version it describes lives in =bash.scm= as
=heks-bash-version= and reaches the generated file, =about= and the tag.

* Unreleased

Nothing yet.

* 2.2.2 - 2026-11-21

No behaviour changed: the Guile half of the configuration is documented by
guile-dokgen, and the two directions the module has are drawn where they are
described.

** Changed

- ~maak docs~ runs ~dokgen~ instead of ~documenta~, writing the API chapter into
  =doc/api= for ~texi2any~ to render as one page with the stylesheet, the script
  and the diagrams beside it.
- ~channels.scm~ pins Guix master ~5cea8de~ and the jointhefreeworld revision
  ~139880f~, which is where ~guile-dokgen~ comes from; ~manifest.scm~ takes
  dokgen from there, so the documentation tasks and the Guile tests are built
  against one pinned revision of the collection.
- Parameters in and rendered chunks out are a mermaid diagram in the README and
  in the Commentary of =bash.scm=, with its source and SVG under
  =resources/diagrams/= and a ~maak diagrams~ task that renders them.
- =bash.scm='s prose section now closes on a real =;;; Code:= marker instead of
  a commented-out one, and the Commentary names the two directions the module
  has — parameters in, rendered chunks out — so the section a reader sees and
  the section dokgen parses are the same one.

* 2.2.1 - 2026-11-18

A documentation release: no behaviour changed, and the only difference a user
can see is the version string.  The point was to make the code explain itself
where it is read, and to write down the one contract that two implementations
share.

** Every function says what it is for

- =bash.scm= has a Commentary that states the split the whole project rests on
  (data here, procedure in the two shell files), the order the rendered file is
  assembled in, and what the entry points are for.  Every parameter carries the
  question it answers - which machine, which alias, which keys, which tools -
  and every serialiser says which shape it renders.
- =shell-lib.bash= opens with a map of its own sections and the order they are
  sourced in, and each function has a first line saying why it exists.  The
  prompt internals carry the detail: which porcelain v2 records are read and
  what each one means, why the palette keeps two copies of every sequence, why
  the theme is asked for once.
- =notes.bash= opens with the notes format itself - the tree, what a note is,
  what the index markers own, the shape of the four side files, how it fails,
  and what it needs - and every one of its 45 functions says what it does, with
  the awk insertion, the picker's three-line output, the index rewrite and the
  birthday arithmetic explained where they happen.
- The test file explains how to add a test to each half, and =maak.scm= lists
  the tasks in the order a contributor meets them.

** The notes format is a document**

- [[file:docs/notes-format.org][docs/notes-format.org]] states the contract
  between `n` and the Emacs side: the tree, the front matter, the index markers
  and the three regions they preserve, `todo.org` and `habits.org`,
  `contacts.org` and `bookmarks.org`, what `n` guarantees about a file it
  rewrites (atomic writes, exit codes, nothing outside the tree), and which
  side owns what.
- The README gains two sections it was missing: what the ten chunks of the
  generated file are and where each comes from, and what the `n` command
  actually does - it was the largest thing in the project and had no page.

** Fixed**

- =ensure-smart-emacsclient-bin= had a stray `(dirname script-path)` that
  evaluated and discarded its value.

* 2.2.0 - 2026-11-18

The release where the generated files became testable, and where more of the
configuration moved from Bash into Scheme.

** The generated file is tested

- =maak check= is the new gate.  It runs the Guile suite
  (=test/heks-bash.scm=) inside the pinned toolchain, runs =shellcheck= over
  the two shell libraries and the rendered rc, and fails on either.
- The suite has two halves.  One asserts the rendered file as data: rendering
  twice gives the same bytes, the version and identity reached the output, every
  alias and greeting was serialised, and the checked-in pager keymap equals its
  rendering.  The other sources the rc in a synthetic =HOME= - the real
  =~/.bashrc= is never touched - and asks a shell: =about= answers, =tools=
  lists the dependencies, =pager-keys= prints the map, =n help= works, a bash
  with =complete= and =bind= disabled stays silent, and nothing at all reaches
  standard error.
- Startup cost is a test: the median of five runs against a budget, currently
  ~20 ms against 700 ms of headroom.
- The first thing that suite found was real: =bind "set ..."= printed "line
  editing not enabled" whenever the rc was sourced by a non-interactive shell.
  The readline bindings now only run where readline listens.

** More of the configuration is data in Scheme

- =bash-pager-keymap= describes the pager keymap once, as =(label (key .
  action) ...)= per lesskey section.  Two renderings come out of it: the
  =lesskey= file =less= reads and the =pager-keys= table.  =lesskey= is now a
  rendering and is still committed, because the sibling repositories carry it;
  =maak render= refreshes it and a test fails when the two disagree.
- =bash-tools= is the one table naming the runtime dependencies - name, probe,
  what it is for, how to install it.  The new =tools= function reports it with
  a present/missing column, and =ai= takes its =eca-cli= install hint from the
  same row instead of spelling it out again.
- =bash-path-prepends= exports a directory only when it exists, so a machine
  without a Guix profile no longer gets dead =PATH= entries.
- =heks-bash-version=: one version string, rendered as =CC_VERSION=, printed by
  the file header and by =about=.

** Rendering and printing

- =install-bash= takes =#:target=, so a test or a reviewer can render into a
  temporary home instead of the real one, and =display-bash=,
  =write-bash-config= and =write-lesskey= are the entry points the tests use.
- =maak render= writes =bashrc.bash= (gitignored) and refreshes
  =src/heks-bash/lesskey=.

** ble.sh is pinned

- =install-ble-sh= fetches the commit in =ble-sh-commit= - version
  =ble-sh-version=, =0.4.0-devel4+95ae551= - instead of cloning whatever the
  branch holds, checks the commit out, updates the vendored submodules from it
  and rebuilds.  =ble-update= still works and takes the pin away; re-running the
  task puts it back.  This is the reproducibility the rest of the project
  already had.

** shellcheck

- =shellcheck= runs as part of =maak check=.  Two real findings were fixed -
  =kport= killed a word-split string and now kills an array of pids, and the
  notes' =__n_topic_name= reused a variable name an array had claimed - and the
  rest are disabled by code in [[file:.shellcheckrc][.shellcheckrc]] with the
  reason written next to them.

** Breaking

- =serialize-bash-path-prepend= now emits a test as well as an export.  A caller
  that concatenated its output into a line of its own still works; one that
  assumed a bare =export= now sees an =[[ -d ... ]] &&= in front of it.
- The =lesskey= file's content changed shape: it is generated, with the bindings
  grouped under comments, so a copy in another repository is stale until
  replaced.  The bindings themselves are the same 41.
